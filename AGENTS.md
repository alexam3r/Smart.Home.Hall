# AGENTS.md

Правила для AI-агентов (Claude Code, Codex, Cursor, DeepSeek Harness и др.), работающих с этим репозиторием.
Читай файл целиком перед любыми изменениями. `CLAUDE.md` импортирует этот файл, поэтому он — единственный источник правил.

> **Коротко:** не менять пины, MQTT-топики, тайминги и порядок ключей JSON; писать код только по блокам плана; после каждого блока — `pio run`, обновление графа, коммит и **пауза** с отчётом.

---

## 1. Что за проект

«Умный коридор» — прошивка контроллера на Wemos D1 Mini (ESP8266):

- LED-подсветка 24 В через ШИМ (4 кГц, 10 бит, кривая CIE1931, плавный переход 2 с);
- тёплый пол через SSR-40 DA (гистерезис ±0.5 °C, авторежим по движению);
- датчики DS18B20 (пол), AM2320 (воздух, I²C), PIR (движение);
- управление и телеметрия по MQTT (Home Assistant / Node-RED).

Идёт архитектурный рефакторинг итерации **Argon**: рабочий монолит `docs/main.cpp` переписывается в модульную прошивку в `src/` + `include/`. Аппаратная часть и наблюдаемое поведение устройства не меняются.

## 4. Команды

PlatformIO может быть не в `PATH`:

```bash
export PATH="$HOME/.platformio/penv/bin:$PATH"

pio run                  # сборка — обязательна перед каждым коммитом
pio run -t upload        # прошивка (upload_speed = 921600)
pio device monitor       # Serial 115200, декодер исключений ESP8266
pio test -e native       # unit-тесты чистой логики
pio run -t clean         # очистка сборки
```

Полная перепрошивка с монитором: `pio run -t upload -t monitor`.

Инструменты:

```bash
export PATH="$HOME/.local/bin:$PATH"
graphify update .        # обновить архитектурный граф (локально, без LLM)
```

Граф: `graphify-out/graph.json` и `graphify-out/GRAPH_REPORT.md` (коммитятся), `graphify-out/cache/` — нет. Перед вопросами об архитектуре читай `GRAPH_REPORT.md`.

## 5. Целевая архитектура

Разбить монолит на независимые модули (ООП). Заголовки — в `include/`, реализации — в `src/`.

| Модуль | Ответственность |
|---|---|
| `Config` | Пины, константы времени, параметры ШИМ, базовый топик |
| `Secrets` | `WIFI_SSID`, `WIFI_PASS`, `MQTT_USER`, `MQTT_PASS`; только `Secrets.h` + `Secrets.h.example` |
| `NetworkManager` | Wi-Fi, MQTT (PubSubClient), фиксированный client ID `ESP8266_Smart_Hall`, подписки, reconnect, watchdog 5 мин, публикации при первом подключении |
| `LightController` | Состояние света, fade, CIE1931 LUT в `PROGMEM`, реверс с текущей точки, таймеры бездействия, публикация статусов |
| `FloorThermostat` | Мастер-режим, авторежим по движению, гистерезис, таймауты, управление SSR, `floor_heat_state` |
| `SensorManager` | Неблокирующий опрос DS18B20 и AM2320, валидация ошибок, обработка фронтов PIR |
| `Telemetry` | JSON каждые 10 с, строгий порядок ключей, `null` при ошибках датчиков |

Требования к реализации:

- `loop()` не блокировать: никаких `delay()`, `requestTemperatures()` с ожиданием 750 мс и прочих синхронных операций в основном цикле. Опрос датчиков — конечный автомат, один шаг за итерацию.
- Бюджет итерации `loop()` — единицы миллисекунд; шаг фейдера идёт каждые 20 мс и не должен «съезжать» из-за сети или датчиков.
- Тяжёлую математику (`pow()` в CIE1931) заменить предрасчитанной таблицей в `PROGMEM`.
- Не плодить глобальное состояние: зависимости передавать через конструктор/ссылки.
- Публикации MQTT не должны блокировать анимацию: `client.loop()` и отправка статусов — в основном цикле, без ожидания подтверждений и без `delay()`; шаг фейдера (20 мс) имеет приоритет.

## 6. Железо и пины (не менять)

| Компонент | Пин Wemos | GPIO | Примечание |
|---|---|---|---|
| LED-лента 24 В, 122 Вт | D7 | 13 | PWM → TC4420 → IRFZ48N; прямая логика: 0 = выкл, 1023 = макс. |
| Тёплый пол, SSR-40 DA 600 Вт | D8 | 15 | Через BS170; активный высокий уровень. |
| DS18B20 (пол) | D5 | 14 | 1-Wire. |
| AM2320 (воздух) | D1 / D2 | 5 / 4 | I²C: SCL / SDA. |
| PIR (движение) | D6 | 12 | Цифровой вход. |

Питание: 24 В → XL4015 → 5 В (Wemos); 24 В → L7812 → 12 В (драйвер MOSFET).

Пины, уровни и схему менять нельзя — устройство собрано и работает.

## 7. MQTT-контракт

Базовый префикс — `home/hall`. Полные payload'ы и таблица топиков — в `README.md` (раздел «MQTT API»). Менять топики, payload'ы, retain и тайминги можно только синхронно с `README.md` и `PRD.md`.

Ключевые инварианты:

- `home/hall/floor/targetTemp` — **camelCase**, float, retain.
- MQTT client ID — фиксированный `ESP8266_Smart_Hall` (без random-суффикса).
- `light_state` публикуется **мгновенно** при команде/триггере; `brightness_state` — **по окончании** перехода.
- `floor_heat_state` публикуется **только при реальном переключении** реле.
- `light/move` — `ON`/`OFF` по фронтам PIR, **без** retain.
- Телеметрия `home/hall/state` — каждые 10 с, без retain.
- При первом подключении к MQTT — один раз опубликовать все `*_state` = `OFF`, `brightness_state` = `100`, `targetTemp` = `30.0` (retain).

Порядок ключей JSON телеметрии критичен (парсится Node-RED/MySQL):

```text
light_state, light_move_state, floor_state, floor_move_state, floor_heat_state,
floor_temp, air_temp, air_hum, pir_raw, since_move_s, uptime, heap
```

Ошибки датчиков (`-127`, `85`, `NaN`, невалидный `0 °C` для пола) отдавать как `null`, а не как число.

## 8. Инварианты поведения (не сломать при рефакторинге)

1. **Безопасный старт.** После подачи питания всё выключено. PIR игнорируется первые 10 секунд (прогрев).
2. **Раздельные таймеры.** `lastLightMoveTime` и `lastFloorMoveTime` независимы. PIR сбрасывает **оба**; любая MQTT-команда света (включая `light/brightness`) — только таймер света; любая MQTT-команда пола (включая `floor/targetTemp`) — только таймер пола.
3. **Защита от underflow.** Сравнения `millis()` — только через `(now - last) >= interval` с `unsigned long`; не сравнивать абсолютные метки и не писать `now > last + interval`.
4. **Свет:**
   - таймаут 1 мин при `moveDetection == ON`, 1 ч при `OFF` (защита от забывчивости);
   - реверс: обратная команда во время перехода плавно разворачивает яркость с текущей точки;
   - фейдер считается по прошедшему времени (`millis()`), номинал 2 с; пропущенный тик не должен «замораживать» анимацию;
   - **ловушка Home Assistant:** `userBrightnessPercent` сбрасывать в `100` **только при выключении**; при `ON` использовать текущее значение (HA шлёт `brightness`, затем `ON`).
5. **Пол:**
   - гистерезис ±0.5 °C от `targetTemp`; мгновенный пересчёт при командах — по последнему валидному измерению, без принудительного чтения датчика;
   - если `floor/moveDetection == ON` и сработал PIR — мастер `floor_state` сам включается;
   - таймауты: 1 ч при `ON`, 12 ч при `OFF`; по истечении мастер выключается и публикуется `floor_state = OFF`;
   - fail-safe: если валидных данных о температуре пола нет дольше 90 с, нагрев выключается.
6. **Датчики.** AM2320 — раз в 15 с, DS18B20 — раз в 30 с; чтение DS18B20 асинхронное (запрос → ожидание → чтение), `loop()` не блокируется. Отдельные топики температур/влажности **не публикуются** — только в телеметрии.
7. **Сеть.** При потере связи — реконнект; если связи нет более 5 минут — `ESP.restart()`.

## 9. Рабочий процесс (обязательный)

PRD §5 задаёт строго итеративную работу. **Не писать весь код сразу.**

1. **Шаг 1 — анализ и brainstorming.** Прочитать `docs/main.cpp`, разобрать причину зависаний 1–2 с при розжиге, предложить решение, задать вопросы человеку. Скилл: `brainstorming` (в PRD — `obra/superpowers:brainstorming`).
2. **Шаг 2 — план.** Детальный поэтапный план по блокам. Скилл: `writing-plans` (в PRD он назван `obra/superpowers:write-plans` — это устаревшее имя).
3. **Шаг 3 — реализация по блокам.** После **каждого** блока, без исключений:
   1. `pio run` — сборка без ошибок;
   2. обновить архитектурный граф в **graphify**;
   3. коммит + пуш с осмысленным сообщением;
   4. **пауза** и отчёт человеку; следующий блок — только после явной команды.

Блоки:

| № | Содержание |
|---|---|
| 1 | Инфраструктура: `platformio.ini`, `Secrets.h` + `.example`, `.gitignore`, базовые модули |
| 2 | Датчики и устранение блокировок |
| 3 | Свет: `LightController`, LUT CIE1931 |
| 4 | Тёплый пол: `FloorThermostat` |
| 5 | Сеть, MQTT, телеметрия |

Дополнительно:

- **graphify** — первичный граф построен (`graphify-out/`). После каждого блока — `graphify update .` и коммит `graph.json` + `GRAPH_REPORT.md`. Если команда недоступна — сообщить человеку, а не пропускать шаг молча.
- Для бага с фризами использовать `systematic-debugging`: сначала воспроизведение и измерения (время итерации `loop()`, `millis()`, heap, логи), потом гипотезы, потом фикс. Без данных не «оптимизировать».
- Перед заявлением «готово» — `verification-before-completion`: показать вывод сборки и перечислить, что проверено вручную.
- TDD применим к чистой логике (кривая, гистерезис, таймеры); фреймворк настроен (`pio test -e native`), железо проверяется вручную.

## 10. Соглашения по коду

- C++17 (`-std=gnu++17` в текущем ядре ESP8266), Arduino core ESP8266; отступ 4 пробела, UTF-8, LF. RTTI и исключения платформой отключены — не полагаться на них.
- Комментарии и сообщения в Serial — по-русски, как в легаси.
- Классы — `PascalCase`, методы и переменные — `camelCase`, константы — `UPPER_SNAKE_CASE` (сохраняем стиль легаси).
- `const`/`constexpr` вместо «магических чисел»; все пины и тайминги — в `Config.h`.
- Строки MQTT-топиков — `const char*`/`constexpr`, без склейки `String` в горячем пути.
- JSON — `StaticJsonDocument` фиксированного размера, буферы — статические; не выделять память в `loop()` (фрагментация heap на ESP8266).
- Проверять все возвраты и корректность данных датчиков; ошибки шины не должны попадать в телеметрию как значения.

## 11. Безопасность

- Пароли и ключи — только в `include/Secrets.h`, который добавлен в `.gitignore`. В репозитории — только `Secrets.h.example` с заглушками.
- Не логировать пароли, не вставлять реальные креды в PRD/README/тесты/сообщения коммитов.
- Если секрет уже попал в коммит — сообщить человеку; историю git самостоятельно не переписывать.
- Не добавлять в телеметрию приватные данные сверх оговорённого контракта.

## 12. Проверка и Definition of Done

Блок считается готовым, когда:

- [ ] `pio run` завершается успешно (приложить хвост вывода);
- [ ] `pio test -e native` проходит для затронутой чистой логики;
- [ ] модуль не блокирует `loop()` и не ломает 20-мс шаг фейдера;
- [ ] MQTT-контракт и порядок ключей JSON не изменились (или изменение согласовано и отражено в README/PRD);
- [ ] проверены соответствующие сценарии: старт «всё выключено», первые публикации, таймеры, реверс, гистерезис, reconnect;
- [ ] граф graphify обновлён;
- [ ] коммит и пуш сделаны, человеку отправлен отчёт;
- [ ] в отчёте честно указано, что проверено на железе, а что — только сборкой.

## 13. Git

- Один блок — один (или несколько логичных) коммитов; не смешивать несвязанные изменения.
- Сообщение — императив с областью: `feat(light): LUT CIE1931 вместо pow()`, `fix(floor): гистерезис при граничной температуре`, `docs: описание MQTT-контракта`.
- В коммит не попадают: `include/Secrets.h`, `.pio/`, `.dsh/`, локальные `.vscode`-файлы из `.gitignore`.
- Push — после каждого блока (PRD §5). Работа в отдельной ветке и PR — только по договорённости с человеком.
- Не переписывать историю (`rebase`, `push --force`) без явного разрешения.

## 15. Принятые решения

Открытых вопросов нет. Все уточнения зафиксированы в `PRD.md` §6:

- любая MQTT-команда зоны (включая `brightness` и `targetTemp`) сбрасывает таймер этой зоны;
- MQTT client ID — `ESP8266_Smart_Hall`;
- `0 °C` на полу — ошибка датчика, в телеметрии `null`;
- reconnect — не чаще одного раза в 5 секунд, watchdog 5 минут сохраняется;
- DS18B20 опрашивается раз в 30 с (асинхронно), AM2320 — раз в 15 с;
- команды пола используют последнее валидное измерение; при отсутствии валидных данных дольше 90 с нагрев выключается;
- фейдер считается по прошедшему времени (`millis()`), визуальная плавность важнее строгого числа шагов;
- AM2320 читается одним обменом на цикл; свой драйвер — только если появятся пропуски показаний.
